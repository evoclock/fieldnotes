Building a 4B Local Implementer

Project brief · generated V14 · 15-seed update · 29 July 2026

Julen Gamboa · github.com/evoclock

This project asks a practical question: can a small local AI model learn how I prefer to work and complete well-defined software tasks as part of a supervised model workforce?

The project does not expect one model to do every type of work. A Planner defines the task. An Implementer makes the agreed change. A Reviewer checks the result. The system selects the right model before work starts.

How the Local Model Workforce routes work

Why I started this project

Large frontier models can be capable software assistants. They can also need long instructions, repeated correction, and substantial computing resources. During a long session, a model can lose context or expand the task.

I wanted the system to use a powerful reasoning model for planning and difficult decisions, and a smaller local model when the task was already clear. Authority, project state, and evidence remain outside the model.

Teaching the model how I work

All training examples came from software projects that I wrote myself. My repositories already recorded my instructions, accepted changes, checks, and corrections. I turned that real history into examples of how I define, implement, check, and complete work.

The goal was to teach working habits, not only writing style. The model should stay within the agreed task, make the requested change, check the result, and report the outcome honestly without having every convention re-explained.

The second experiment started with Jan Code 4B and used 2,156 examples from my projects. Training took 3.44 hours on one local NVIDIA DGX Spark.

What improved

The fine-tune taught the intended task-bound Implementer role. On 86 shared implementation tasks, correct action selection rose from 0.0% to 90.7%. Correct scope and valid response structure each reached 94.2%.

The tuned model returned usable implementation material in 90.70% of cases, compared with 43.02% for the original model. The returned implementation could be executed in 59.30% of cases, compared with 43.02% before fine-tuning.

Testing the role with the right benchmark

HumanEval+ gives the model a short and complete function specification. This is a good direct test of whether the 4B Implementer still writes correct code.

Some AIME and difficult LiveCodeBench tasks require algorithm discovery or deep decomposition. They are better tests of the reasoning Implementer or Planner. A low 4B score can show a routing mismatch rather than ordinary coding loss. Real repository-card trials are the closest test of the deployed role.

What happened to general coding ability

I repeated the HumanEval+ comparison 15 times for each model. Each pair used the same tasks and seed, with matched sampled decoding. The overall mean and median combine a global taxonomy of task types, so they must be read with the category and sub-task results below.

The tuned model was 2.32 percentage points behind on average. The median difference was 2.44 points. The results varied: two runs favoured the tuned model, while the remaining runs favoured the original.

HumanEval+ results across 15 paired runs

The task-level evidence shows a mix of gains and losses. The tuned model improved on work with lists and collections, text processing, and numeric calculations. It was weaker on some parsing, aggregation, transformation, and ordering tasks. The named sub-tasks show where the effects occurred; they do not, by themselves, prove which training example caused each effect.

Where fine-tuning gained and lost ground
Specific sub-tasks behind the category effects

We prefer no loss in coding ability, but fine-tuning behavioural preferences can affect general capability. The project therefore set a self-imposed three-percentage-point review margin: a larger mean decrease requires corpus-level review, modification, and further fine-tuning. The estimated mean effect remained inside that margin. The repeated evidence confirms that v7 achieved its task-bound role adaptation while retaining broad coding capability, and gives v8 a precise correction path.

Why the workforce design is useful

A clear task can go to the 4B task-bound Implementer. Harder specified work can go to a reasoning Implementer. An unclear objective can go to the Planner. The Reviewer checks the result before acceptance.

Every role feeds evidence into a parallel improvement process. The flywheel finds the first point at which work went wrong and routes the remedy to training, a contract, a test, a tool, documentation, or the runtime. Only grounded and independently reviewed evidence can enter later training.

Closing thoughts

This result indicates that the 4B fine-tuned model can be used in the task-bound Implementer role. It learned the intended protocol, retained broad coding capability, and improved several task types. Once v8 patches the identified loss-producing sub-task types, I expect the next comparison to show a slight overall coding-capability gain, even though that was not the aim of the fine-tune.

Jan Code v8 will preserve the role and capability gains and address parsing and formatting, aggregation, general transformation, and searching and ordering. My authored repository and GitHub history will supply grounded examples that exercise the affected skills. HumanEval+ remains evaluation-only.

The interim harness-neutral MCP server capability will add safeguards that can remain useful after v8 is validated. New evidence must pass causal review and remain separate from hidden evaluation families. V8 will be compared with both the original model and v7.
